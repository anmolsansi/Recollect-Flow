# OPE-221: Implement retry-safe Notion synchronization worker

## Context

RecollectFlow projects its items to Notion for human review. We need a background service that safely syncs D1 items to a Notion Database.

## Requirements

1. Implement `NotionSyncService` in `apps/worker-api/src/sync/notion-sync.service.ts`.
2. The service should use the raw `fetch` API for Notion interactions to keep worker bundles lean. It needs a Notion Integration Token and Database ID (provided via `Env`).
3. It must pull jobs from `sync_attempts` where `destination = 'notion'` using the `JobService` implemented in OPE-246.
4. Sync logic:
   - Map `items` record to Notion Database properties matching the OPE-220 schema.
   - If `items.notion_page_id` is null, create a new Notion page and update D1 with the page ID.
   - If `items.notion_page_id` is present, update the existing Notion page.
   - Truncate texts safely if they exceed Notion's 2000 character limit for rich text blocks.
5. On success, complete the sync job. On failure (e.g. rate limit `429`, or validation error `400`), fail the job using `JobService.failJob(..., retryable)`.
6. Add unit tests for `NotionSyncService` using mocked `fetch` and D1 repository.

## Files to inspect

- `apps/worker-api/src/jobs/job.service.ts` (From OPE-246)
- `docs/NOTION_INFORMATION_ARCHITECTURE.md`

## Definition of Done

- Service correctly creates and updates Notion pages.
- Service respects `sync_attempts` retries and backoff.
- Tested and handles Notion rate-limits (HTTP 429) via standard retry backoff.
- `items.notion_page_id` is properly persisted.

## Completion evidence

- `NotionSyncService` performs an exact Capture ID lookup before create, adopts
  one existing page, and fails safely if duplicates exist.
- Updates include only D1-owned properties, preserving all human-owned Notion
  fields. A missing/deleted page is terminal until the owner/admin recreation
  endpoint is called.
- Requests are paced at least 350 ms apart, time out after 15 seconds, and honor
  `Retry-After` for 429/529 responses.
- The scheduled worker leases up to 25 due Notion attempts per run, persists the
  page ID/projection metadata atomically, and uses the OPE-246 retry contract.
- Unit and workerd-backed D1 integration tests cover create, adopt, update,
  preserved human edits, duplicate pages, deletion approval, rate limits,
  retries, and persistence.
- Production Worker version `c0386c81-15a3-4cb6-a21c-f565f789fc1b` completed
  all 11 seeded Notion sync attempts. All 11 live items have a page ID, last
  successful sync timestamp, and projection hash; no completed attempt retains
  an error code.
