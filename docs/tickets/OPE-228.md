# OPE-228 — Backup, export, deletion, and recovery workflows

Status: implementation in progress

## Goal

Ensure the owner can recover or leave RecollectFlow without losing canonical knowledge while permanent deletion remains explicit, auditable, privacy-preserving, and recoverable across partial external failures.

## Frozen architecture

OPE-228 implements the existing hardening decisions without changing them:

- ADR-001: D1 is the canonical system of record.
- ADR-002: private R2 stores attachment bytes.
- ADR-003: Notion is a review projection, not canonical authority.
- ADR-009: raw source and the original user reason are immutable evidence until an explicit canonical purge.
- ADR-013: deletion is recoverable soft-delete grace followed only by an explicit purge.
- ADR-021: a missing/deleted Notion page cannot silently recreate itself without the existing approved recovery flow.
- ADR-031: verified hosted backups are immutable, expire after 30 days, and purge receipts prevent later restore from silently resurrecting purged items.
- ADR-032: only an explicit RecollectFlow/D1 workflow may initiate permanent canonical deletion. Notion is a downstream purge step.

## V1 recovery model

### Soft delete

The existing `POST /api/v1/items/:id/delete` route remains the reversible grace state. V1 does not automatically promote a soft delete into permanent deletion. The grace period therefore lasts until the owner explicitly starts and confirms a purge.

### Permanent purge

Permanent deletion is a two-step admin workflow:

1. request a purge for a currently soft-deleted item;
2. explicitly confirm the generated request before its confirmation window expires.

A confirmed purge is durable and step-based rather than described as cross-system atomic. The workflow keeps enough non-content operational state to retry incomplete external cleanup.

Initial purge step order:

1. freeze/cancel item processing work;
2. remove linked private R2 attachment objects;
3. archive/remove the Notion projection when one exists;
4. delete item-owned D1 content and derived rows;
5. retain a non-content purge receipt and mark the workflow complete.

D1 canonical content is removed only after required external identifiers have been used for cleanup. If R2 or Notion cleanup fails, the workflow remains partial/retryable and the soft-deleted D1 item remains available for recovery/reconciliation.

### Purge receipts

Purge receipts contain identifiers and operational timestamps only, not source content, notes, derived text, prompts, provider responses, or attachment bytes.

Receipts are intentionally retained beyond hosted backup expiry so recovery tooling can reject an old owner-controlled backup that contains an item which was later permanently purged.

## Portable export

Admin export supports JSON and CSV.

JSON is the full-fidelity portable format and includes:

- export schema version and generated timestamp;
- canonical item fields;
- original capture/provenance events;
- user notes/reasons;
- derived item fields and override metadata;
- processing job states/results;
- sync attempt state;
- attachment references and integrity metadata, never attachment bytes;
- extraction metadata/results;
- feedback and safe audit history;
- provider usage metadata;
- current non-content purge receipts.

CSV is an owner-readable item-level projection. Related collections are represented as JSON cells where flattening would lose structure. CSV is not the canonical restore format.

Exports never include credentials, session cookies, provider tokens, `.dev.vars`, environment secrets, raw hosted backup object bytes, or private R2 authorization material.

## Hosted backup

A hosted backup is a portable JSON snapshot written to a private R2 `backups/` prefix and registered in D1.

Requirements:

- object keys are unique and never overwritten;
- the serialized payload is SHA-256 hashed before write;
- the stored object is read back and verified before the backup is marked complete;
- completed artifacts are immutable through application routes;
- normal retention is exactly 30 days;
- expiry cleanup may remove the R2 object after retention while retaining non-content backup audit metadata;
- backup creation failure never mutates or deletes live canonical data.

## Restore

The JSON restore path supports validation/dry-run and clean-database restore.

Restore must:

1. validate schema/version before writes;
2. validate internal identifiers/references;
3. merge the newest available purge-receipt ledger;
4. remove/reject records covered by purge receipts before canonical item insertion;
5. restore canonical item/capture/derived/job/sync/attachment-reference data;
6. rebuild search usability through normal D1 triggers/indexes;
7. run post-restore integrity checks;
8. refuse to report success when receipt application or integrity verification fails.

Owner-downloaded backups are outside RecollectFlow's remote deletion control. Documentation must state this explicitly.

## Integrity checks

OPE-228 adds read-only checks for:

- D1 attachment rows whose linked R2 object is missing;
- R2-linked attachment rows pointing at missing items;
- linked/finalized attachment state mismatches;
- items with a stored Notion page ID that the provider reports missing;
- purge workflows that remain partial or retryable;
- backup artifacts whose verification metadata is incomplete or expired.

Integrity checks report findings; they do not automatically purge canonical content.

## Stable workflow states

Backup: `creating | verifying | complete | failed | expired`

Purge: `confirmation_pending | queued | processing | partial | complete | cancelled`

Purge step: `pending | processing | complete | failed | skipped`

Restore: `validating | restoring | verifying | complete | failed`

Integrity run: `running | complete | failed`

## Acceptance matrix

- [ ] full JSON export is independently readable and schema-versioned;
- [ ] CSV export is independently readable;
- [ ] export includes items, notes, derived fields, job states, and attachment references;
- [ ] exports contain no credentials/secrets;
- [ ] hosted backup object is content-hashed and read-back verified;
- [ ] completed hosted backups cannot be overwritten through the application;
- [ ] hosted backup retention is bounded to 30 days;
- [ ] backup failure leaves live D1/R2/Notion item state unchanged;
- [ ] soft delete remains reversible until explicit purge confirmation;
- [ ] purge request requires a soft-deleted canonical item;
- [ ] permanent purge requires a separate explicit confirmation action;
- [ ] purge confirmation expires and cannot be replayed;
- [ ] Notion deletion/missing state never initiates D1 purge;
- [ ] R2/Notion purge failure leaves durable partial/retryable state;
- [ ] completed purge removes active D1 canonical/derived data and R2 bytes;
- [ ] completed purge leaves a non-content receipt;
- [ ] restore applies purge receipts before inserting canonical items;
- [ ] a pre-purge backup cannot silently resurrect a purged item when a newer receipt ledger is supplied;
- [ ] restore into a clean local D1 recreates searchable usable records;
- [ ] orphaned/missing attachment integrity findings are reported safely;
- [ ] missing Notion projections are reported without triggering canonical deletion;
- [ ] recovery and D1 backup/restore procedures are documented and tested;
- [ ] repository quality gate, migration rehearsal, and Wrangler dry-run pass.

## Commit discipline

OPE-228 is intentionally developed as at least 50 small, reviewable commits. Every counted commit must introduce a real contract, schema unit, behavior, focused test, integration, documentation improvement, or validation fix. Empty/no-op commits do not count.
